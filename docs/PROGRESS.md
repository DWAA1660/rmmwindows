## 2026-11-04 — Agent 0.1.1: automatic update at service startup

- Flow: GET `/api/agent-download` from the enrolled origin (no redirects, TLS validation on) → accept only a strictly newer plain `x.y.z` win-x64 package at the fixed `/downloads/library-rmm-agent-win-x64.zip` path → persist the attempt in `%ProgramData%\LibraryRmm\updates\update-state.json` BEFORE downloading → stream the download with size and SHA-256 checks → extract with path-traversal and size limits → verify the inner `package-manifest.json` version and agent exe SHA-256 → launch a detached `apply-update.ps1` that runs the package's own `Install-Agent.ps1` (enrollment preserved, only LibraryRmmAgent restarted, never reboots). ## 2026-11-04 — Live sfc/dism progress through a pseudo-console relay

- Problem (seen on RESEARCH): `sfc /scannow` progress arrived in bursts about 90 s apart, each ending mid-word. sfc fully buffers about 4 KB when its stdout is a pipe, so nothing the agent does with the pipe can make it sooner; the program has to believe it writes to a console.
- `agent/ConsoleRelay.cs`: `LibraryRmm.Agent.exe --console-relay <program> [args]` (dispatched in `Program.cs` before every other argument check). It creates a ConPTY pseudo console (512 columns x 2000 rows), starts the program attached to it (suspended, put into a kill-on-close job object, then resumed), reads the VT output on a background thread, converts it to text and writes UTF-8 to its own stdout with a flush after every read. After the program exits it drains until the console is quiet for 300 ms (max 3 s), closes the pseudo console, flushes, and exits with the program's exit code. Program lookup: explicit paths as given, bare names on PATH only (never the current directory); not found = exit 9009 with a message. Command line rebuilt with standard Windows quoting (round-trip tested with `CommandLineToArgvW`).
  - Gotcha confirmed empirically: without `STARTF_USESTDHANDLES` the child inherits the relay's redirected stdout pipe (the test child reported `console=False` and would buffer as before). The relay sets the flag with null output handles, so stdout/stderr are the pseudo console (`console=True`).
  - Stdin is the NUL device (only that handle is inherited, via a handle list), so a program that reads stdin gets end-of-file immediately, exactly like a normal job. Nothing is ever typed into the console. A program that opens the console input directly (CONIN$) would wait until the job timeout.
  - Without ConPTY (before Windows 10 1809 / Server 2019) or if creating it fails, the relay prints one line to stderr and runs the program directly with its own standard handles (old behavior: bursts). This fallback only happens before the program starts, so it never runs twice.
  - Process tree: the relayed program and its conhost.exe are children of the relay, so the job timeout's `Process.Kill(entireProcessTree: true)` ends them (tested by PID). If the agent stops reading (stdout broken), the relay exits and the job object ends the program.
- `agent/VtTextConverter.cs`: models the screen because ConPTY sends minimal diffs (for example only the `6` at `ESC[3;14H` when 5% becomes 6%). New rows are emitted after CRLF; when the last emitted row changes it is re-emitted after `\r` (or only the appended suffix). Handles cursor movement, erase line/screen, delete/erase/insert characters, scrolling (LF at the bottom, `ESC[S`, delete line at top), OSC/DCS strings, SGR and private modes (dropped), escape sequences and surrogate pairs split across reads, East Asian wide characters (two cells) and soft-wrapped rows (a line wider than 512 columns is joined back without a break).
- `PowerShellRunner.cs` wrapper now defines `Invoke-LiveConsole` (a simple function: `& <agent exe> '--console-relay' @args`, so `/scannow`, `-n`, `--x` pass through untouched) plus `sfc` and `dism` functions that call it. A job that says `sfc /scannow` or `dism /online /cleanup-image /restorehealth` therefore streams live. `sfc.exe`/`dism.exe` typed explicitly bypass the relay (escape hatch). `$LASTEXITCODE` is the program's exit code and the wrapper's exit handling is unchanged. Other console tools: `Invoke-LiveConsole <program> <args>`. Bonus: `$x = sfc /scannow` now captures readable UTF-8 text instead of raw UTF-16.

## 2026-11-05 — Persistent terminal fixed, support tests added, feature branch verified (Claude)

- **Terminal blocker fixed** (`agent/TerminalShell.cs`). Root cause: PowerShell is assigned to its kill-on-close job object just after `Process.Start`, and Windows creates its `conhost.exe` during startup, so conhost is inside the job only sometimes; the old `ActiveProcesses > 1` rule then ended a normal first command. Now, once PowerShell has connected (membership settled), the shell records a baseline of job members, accepting only itself plus the genuine `%SystemRoot%\System32\conhost.exe` (full image path). After each command any other live job member (after a 1 s grace for exiting processes) is a real detached background process: the terminal ends and the job object kills it.
- **Output-retention failure stops the command immediately**: the boundary read is raced against stdout/stderr pump faults, so a durable-spool failure ends the shell within seconds instead of at the command timeout. Any exception now ends the shell (previously only some types were caught).
