# Park County Library RMM

## Initial design — 2026-11-04

Self-hosted Linux application at https://rmm.parkcountylibrary.org. Node 24 LTS/Express API with SQLite WAL durable state, React/Vite console, .NET 10 LTS Windows worker service installed as LocalSystem. Agents make outbound HTTPS requests only. SQLite and output live in a persistent Docker bind mount. Existing host websites must remain operational.

## Safety and delivery semantics

Jobs are at-most-once, not exactly-once. Server atomically consumes a queued job into dispatched; it never dispatches it again. Agent obtains an explicit durable start authorization before side effects. A second start request cannot authorize another execution. Lost responses may prevent execution; operator must inspect and create a new job. This prioritizes avoiding repeat reboots/scripts with Reboot Restore over automatic recovery. Local agent journals improve output recovery but are not the replay authority. A restored endpoint snapshot cannot reset server job state.

Job kinds: `powershell`, `reboot`, `inventory`, `storage`, `files` (remote file explorer: list/delete/move/copy/rename/mkdir/download, one operation per job, see API.md). Agents long-poll `jobs/claim` (`waitSeconds:20`) so a queued job starts within moments; the claim is the same single atomic transaction, so long-polling does not change at-most-once semantics. Folder downloads (agent 0.1.13+) are compressed on the endpoint into one zip inside the agent's protected data folder, sent like a file, then deleted. Uploads (schema 11, agent 0.1.14+) go browser -> server in 4 MiB chunks to UUID-named files beside the database (owner-only, size reserved against the shared cap, server-side SHA-256), then one at-most-once `files`/`upload` job per computer fetches the bytes only while it is running and moves them into place after verifying size and hash. Remote zip extraction refuses zip-slip names, links and protected folders, and checks declared sizes and CRC-32 per entry. Write destinations are checked against the safety policy by their real final path (links and 8.3 names resolved). File downloads are uploaded in raw chunks to disk beside the database (bounded by per-file/total caps and 7-day expiry), never into the web root. PowerShell is noninteractive, hidden, elevated by LocalSystem service identity. Each job is a fresh PowerShell process, not a persistent interactive console. Output uses sequenced chunks and server-side deduplication, supports stdout/stderr, pagination and full attachment download. A shell command using formatting commands can itself truncate text; server preserves exactly what the process emits.

Web authentication uses password scrypt and opaque HttpOnly sessions; agent credentials are separate, random, hashed in server database. Enrollment tokens expire and have use limits. All command creation, enrollment, settings, and changes are audited. No external unauthenticated command path. Remote support uses a visible per-user companion and a session-scoped relay, described below; no covert viewing.

## Remote support

0.1.12 lifecycle correction: closing a bootstrap pipe must not let StreamWriter's cleanup exception strand the lease as active. HelperChannel disposal is idempotent, closed-channel heartbeats are refused, and the lease's Finished flag is unconditional. WTS lock detection reads the x64 WTSINFOEX SessionFlags at byte16, separately from SessionState at byte12. Existing approval/indicator settings and session policy snapshots are unchanged by this maintenance fix.

An operator opens a dedicated browser window for one endpoint. An internal `remote_support` job passes the ordinary durable at-most-once start gate, then the LocalSystem service launches the support helpers (agent 0.1.11+ design below; 0.1.6–0.1.10 launched one non-elevated WinForms companion that did capture, input and the notice). A random one-use named pipe per helper verifies both process identities; only the SYSTEM screen helper's pipe (SYSTEM-only ACL) carries the short-lived support credential, never the agent credential. The launch job completes independently of the live support session; neither automatically reconnects or replays.

**Takeover (2026-11-05, per the user's request that a new session "override the old one").** Creating a session for an endpoint that still has an open one ends the old one first (`stopped`, reason `replaced_by_new_session`, audited with the new operator; any unconsumed launch job is cancelled, consumed ones are never replayed). On the endpoint, a new authorized launch terminates the previous lease's helpers and any stray `LibraryRmm.Support.exe` from the install folder before starting. Previously the agent refused with "A remote support session is already running on this computer".

**Screen helper + notice (agent/companion 0.1.11, per the user's request that signing in with Ctrl+Alt+Delete must not end or lag the session).** Every session uses one SYSTEM *screen helper* in the target Windows session (console preferred, else the only active session): the service copies its LocalSystem token into that session (`TokenSessionId`) and starts the fixed companion with `--mode engine`. It creates no windows. A capture thread and a separate input thread each switch to the session's current input desktop (`OpenInputDesktop`/`SetThreadDesktop`) before every operation, so the regular desktop, Ctrl+Alt+Delete, lock, sign-in and UAC screens all keep streaming and stay controllable, and input never waits behind a capture. When a user is signed in and the snapshot has the approval notice or the indicator on, the service also starts the same executable non-elevated as that user with `--mode notice`: it shows the approve/decline form and countdown (expiry approves, decline/close refuses), then the persistent topmost indicator, and registers Ctrl+Alt+Shift+F12. The notice has no relay credential and never captures, injects or touches the network; it sends `consent{approved,control,decision}`/`stop{reason}` to the service, which adds the user name from the token and relays to the screen helper. Pipe messages are strict fixed-shape JSON lines (`SupportPipeMessages`).

What the screen helper shows (`SupportAccessPolicy`): nobody signed in → sign-in screen, consent `signin_screen`; a locked session's lock/Ctrl+Alt+Delete screen → shown before consent (no user content; consent `signin_screen`, user `Windows lock screen`) so the operator can unlock; a signed-in user's own desktop, or an unlocked UAC prompt (whose background is a dimmed picture of their desktop) → only after the notice approves, unless both notice and indicator are off. If someone signs in during a sign-in/lock-screen session the helper pauses (`waiting_for_user`), asks the service for a notice in the new user's session, and resumes after it approves (device message `userConsent`, audited with `phase:"user_signed_in"`; declining ends the session as declined). Closing/killing the notice ends sharing (`notice_closed`). Remote clicks/keys cannot reach the notice window (checked by owning process). Ctrl+Alt+Shift+F12 is also polled on every desktop by the screen helper. Native Ctrl+Alt+Delete is still `SendSAS` from the service honoring `SoftwareSASGeneration` (impersonating the signed-in user's limited token, or directly when nobody is signed in); it is never a key chord. Because the helper is SYSTEM, input also reaches elevated windows. Sign-out or restart ends the session (the helper's Windows session ends); start a new one, which now works at the sign-in screen.

**Frames (0.1.11).** The helper captures the selected monitor (GDI, 24-bit, at most 1920 px wide; smaller screens at full resolution) and sends `RMF1` frames: a keyframe repaints the surface, other frames carry only changed 64-px tiles merged into ≤64 rectangles (JPEG each; >55% changed → full repaint), and a header-only frame is a 1-second heartbeat for a still screen. The browser acknowledges each frame (`frameAck`); the helper keeps at most two unacknowledged, so the picture never queues behind a slow link (~15–20 fps on changes, ~8 checks/s when still). The relay drops patches after a dropped frame or a resume until the next keyframe and asks the helper for one (`keyframe`); the browser can ask too (`refresh`). Capture failures during desktop switches are retried (ending only after ~15 s of continuous failure), and SendInput refusals are ignored instead of ending the session.

Admin-only settings persist the staff-notice policy: enabled by default,15seconds, configurable1–300seconds. Per the user's latest instruction, timeout approves; decline/closing refuses. The admin may disable the form for an already signed-in unattended VM. New sessions snapshot these settings, so editing policy cannot change an in-progress notice. Every mode requires a persistent topmost sharing indicator and a functioning displayed Ctrl+Alt+Shift+F12 local emergency end shortcut; no staff Stop button. The browser operator retains End session. There are no frames or inputs before the local notification policy completes and the operator is connected.

Before 0.1.11: the user-mode companion captured the primary display and visible cursor as memory-only whole JPEG frames, at most 1600 pixels wide/about 3 fps, sent SendInput subject to UIPI, could not view/control Winlogon, lock screens, UAC secure desktops or higher-integrity applications, and paused on desktop changes until a local Resume (or ended in hidden mode). This is why Ctrl+Alt+Delete ended or froze sessions. The relay still accepts these agents' whole-JPEG frames.

**Sign-in screen mode (agent 0.1.10 only; superseded by the 0.1.11 screen helper above, which no longer ends when someone signs in).** When no user is signed in at the console, or the console session is locked and the session snapshot has both the approval notice and the indicator off, the service copies its LocalSystem token into the console session (`TokenSessionId`) and starts the same fixed companion executable on `WinSta0\Winlogon` with `SignInScreen:true` in the pipe bootstrap. The pipe ACL is SYSTEM-only; the companion refuses sign-in mode unless it runs as SYSTEM and refuses normal mode if it does. This mode creates no windows: one window-less MTA thread switches to the current input desktop (`OpenInputDesktop`/`SetThreadDesktop`) before every capture, input and keyboard check, so sign-in, lock, Ctrl+Alt+Delete and UAC screens are shown and controlled. There is no person to notify, so it consents with decision `signin_screen` (accepted by the relay even when approval is required; audited). Ctrl+Alt+Shift+F12 at the computer is polled with `GetAsyncKeyState` and ends the session. When a signed-in user's `Default` desktop appears, the session ends (`user_signed_in`) unless the snapshot has both notice and indicator off, in which case it continues on that desktop as SYSTEM. If the console moves to another Windows session the stream pauses and ends after 30 seconds. Ctrl+Alt+Delete is requested by the service directly (no impersonation), still honoring `SoftwareSASGeneration`. **Not yet verified on a real endpoint.**

The unprivileged web server relays same-origin WebSockets without recording frames or keystrokes. Browser tickets are one-use,30seconds, bound to the creating login session; device grants are one-use and endpoint/session/job scoped. One controller and one companion per session; all sessions end on disconnect, account/logout revocation, endpoint revocation, expiry or server restart. Maximum session30minutes. Audit records lifecycle and policy changes, never image/key content or secrets. Backpressure may drop stale live frames; durable command output remains fully retained on its separate transport.

Schema v6 adds support sessions/tickets; additive v7 adds persistent admin policy and immutable per-session snapshots. The current relay is single-process; horizontal replicas need deliberate shared ownership/routing. Nginx must forward Upgrade/Connection for `/api/support/`; the application gets no Docker socket or additional public port.

## Updates

Schema v5 adds organizational endpoint groups and persisted job-run snapshots. Installer and approval flow is unchanged; the database default assigns all newly inserted agents to permanent New endpoints. Each endpoint belongs to one group. Moving/deleting groups changes organization only, never agent credentials or queued/dispatched jobs. Bulk run membership is a launch-time snapshot; group changes do not add targets or replay work. Existing global roles apply; groups do not create permission boundaries.

Account schema v2 adds email, role and disabled fields in an additive transaction; existing administrators and credentials are preserved. Roles are checked against current database state for each request. Password changes/reset, disabling and role changes delete affected sessions. All sensitive account mutations require acting-user password confirmation and CSRF/origin checks, with rate limiting. Preserve at least one enabled administrator. Email is contact-only; no SMTP/reset-email workflow is configured. Do not roll back to pre-account-management images after creating restricted users, as older code does not enforce these roles.

GitHub Actions builds an image in GHCR. The initial host update service uses a separate read-only deploy key to fetch private GitHub `main` and build a commit-tagged local image, preserving data and restarting only this stack after health checks. This avoids storing broad GitHub PAT/GHCR credentials on the shared host. Admin UI requests updates via a narrowly scoped authenticated update helper; Docker socket is never exposed to the web container. The helper and Compose config are reviewed host files outside the auto-updated checkout. Pending/running jobs are never requeued during upgrades. A failed revision is not automatically retried until a new commit arrives; manual retry is explicit.

### Agent updater evidence — schema9

Agents0.1.8+ send structured updater status through ordinary checkin and a dedicated bearer-authenticated `/api/agent/update-status` path, allowing startup progress before inventory or jobs begin. This evidence is separate from inventory. Missing telemetry from an older agent remains explicitly unknown; the server never diagnoses a failed update from version age alone. Endpoint receipt time uses the server clock, while updater event timestamps retain the agent's reported time.

Only a closed versioned schema with bounded versions/timestamps/counts, known phases/stages/error codes, SHA256 and fixed safe summaries is accepted. Unknown properties and arbitrary exception/transcript text are rejected before atomic heartbeat/report storage. Latest status and at most100 semantic transitions per endpoint live in additive schema9; timestamp-only heartbeats do not append history. Failure audit contains safe metadata only. Updater-history pruning is isolated from durable jobs, output and consumed execution grants. Read-only fleet/endpoint views expose evidence to existing roles; telemetry has no command-execution authority. See `HANDOFF-UPDATE-SERVER.md` for contracts and verification.

## Scope boundaries

Agent distribution is hosted by the app: `/install.ps1`, a public x64 ZIP, and public checksum/metadata. The Docker build cross-publishes the self-contained Windows service and packages the existing administrator installer. Public artifacts contain no enrollment token. An authenticated operator creates a token separately and the installer prompts securely. The bootstrap verifies HTTPS metadata/package SHA256 before extraction; it supports download-only validation without installing a service.

Action1 release deployment integration later. The administrator PowerShell installer packages self-contained agent and support companion binaries. Only the companion subtree permits Users read/execute; agent credentials/spool stay SYSTEM/Admin-only. MFA/SSO, mature alerts, signed installers and Windows secure sign-in support remain follow-up work.
